# Server population polling plan — issue #275

Implementation status: issue #275 is implemented in this branch, with operator feeds disabled by default. This document retains the agreed design and research record; see `docs/population-polling.md` for setup and manual testing.

Issue: https://github.com/amoeba/treestats.net/issues/275

## Agreed direction

- Add operator-hosted population polling, initially for Hollowtide, without requiring players to run Decal or impersonating plugin uploads.
- Start with **one poll every 15 minutes per server**. Faster polling is not part of the initial rollout.
- **Polling is additive.** A server with polling and Decal users contributes both/all streams of population observations to the same history. Neither source replaces or suppresses the other.
- **Store provenance on each new population observation as `source: "plugin"` or `source: "server"`.** Plugin uploads use `"plugin"`; operator polling uses `"server"`. Existing records without `source` are treated as `"plugin"` when read; no bulk backfill is needed. **This PR stores provenance internally only: do not expose it in UI, public APIs, or other public outputs.** Future provenance presentation would concern latest counts only; daily-maximum calculations and historical charts do not need provenance.
- **Polling failure is publicly unobtrusive, even if the entire polling system stops.** Do not add public failure badges, synthesize zero counts, remove otherwise eligible servers, or interfere with Decal ingestion. Latest-count presentation continues using accepted observations and their truthful as-of time, without exposing source in this PR. Do not renew timestamps to conceal a lack of new data. Operational failure visibility is separate from public presentation.
- The endpoint response is a JSON object requiring only **`count`** (a nonnegative integer) and **`updated_at`** (an integer Unix timestamp in UTC seconds representing when the population was measured/refreshed). **Allow and ignore additional fields.** Server identity comes from the approved registration, not response fields; provenance is assigned by TreeStats.
- **Use the same population definition as the game/plugin:** connected, in-world player characters, including bots, multiboxed characters, staff, and test characters. Do not count unique humans/accounts or apply operator-specific exclusions. A measured empty world is valid zero; inability to measure is not zero and must not refresh an old measurement's timestamp.
- Keep knowledge of polling attempts separately from accepted population observations. Fetching the same `updated_at` must not insert another observation or refresh the existing observation's age.
- **Timestamp acceptance: `last_accepted_updated_at < updated_at <= floor(response_received_at_epoch_seconds)`.** No maximum-age gate and no additional future/clock-skew grace. The first measurement has no previous cursor to exceed. Capture actual response-receipt time before parsing/database work, so live measurements generated during the request are accepted. Old but new-to-this-feed measurements are useful history and retain their reported observation time.
- **Bind polled population values to the operator's reported measurement time**, assuming an adequately synchronized clock. Use that time for latest-observation ordering and UTC historical grouping, rather than the time TreeStats fetched the document. For example, a 23:59 UTC measurement fetched at 00:02 belongs to the previous day.
- Operators choose their own measurement/export cadence. With no maximum-age gate, slow exports yield fewer distinct observations rather than rejection solely for age. Repeated documents do not refresh population age. Frequent refreshes or dynamic measurement improve coverage but are not required.
- **Registration is maintainer-reviewed configuration mapping servers to polling URLs**, separate from autogenerated `data/servers.rb`. Operators request registration through an issue or PR and maintainers verify ownership/approve the URL. No registration API, operator accounts, tokens, admin UI, or automatic endpoint discovery/polling from the community list in this PR.
- **Use the existing Sidekiq setup with one recurring scheduler that enqueues an independent polling job per registered server every 15 minutes.** The scheduler does not perform HTTP requests. Bound concurrency/request duration, prevent overlapping requests for a feed, and keep per-feed outcomes independent. Do not migrate unrelated background jobs.
- **Do not catch up missed polls after downtime.** Resume with a current fetch per due feed rather than replaying historical polling intervals.
- **No automatic retries for polling jobs in this PR.** Record failures and wait for the next scheduled poll. Disable Sidekiq's default automatic retries for these jobs.
- **Keep one mutable polling-state record per registered server**, with last check time, last outcome, bounded error summary, last accepted measurement timestamp, and consecutive failure count. Update it on each check rather than permanently storing each attempt. Accepted observations remain separate append-only population records; failures never enter `player_counts`. Detailed errors go to application logs.
- **Leave existing historical cache policies unchanged in this PR.** Late observations may change past daily maxima in MongoDB but become visible when existing caches expire; do not invalidate historical caches on polling ingestion.
- These semantics and operational choices were resolved for the implementation; this document preserves the research record.

## Existing behavior and research

- Plugin uploads containing `server_population` create `PlayerCount` documents.
- MongoDB stores these in `player_counts`, using `s` (server), `c` (count), and `c_at` (creation/receipt time). There is no provenance field.
- The plugin sends population once after login, rather than repeatedly sending its cached login-time value.
- Historical charts calculate the maximum observation per server per UTC day and exclude today.
- Latest-count readers have separate aggregation paths and caches. Cache warming runs every five minutes; the latest-counts JSON cache lasts six minutes.
- Community server-list entries have stable UUIDs, but the TreeStats importer currently discards them. `data/servers.rb` is autogenerated and should not be edited manually.
- Sidekiq and sidekiq-cron are installed. The Sidekiq boot path now loads the probe and population polling jobs. Cache warming still uses Clockwork/Resque.
- No adopted ACE population HTTP contract was found. Prior work includes the diagnostics discussion (#718), JSON heartbeat proposal (#3446, open/unmerged), API plugin proposal (#1629, closed/unmerged), and Prometheus proposal (#4199, closed/unmerged).
- Broader precedents include game-specific JSON status documents (such as FiveM's `/dynamic.json`) and Prometheus/OpenMetrics gauges at `/metrics`. Neither establishes an AC-specific population JSON schema.

## Initial cadence and volume

At 15-minute intervals, assuming every poll succeeds and produces a new measurement:

| Scope | Observations |
| --- | ---: |
| One server/day | 96 |
| One server/30 days | 2,880 |
| One server/year | 35,040 |
| 50 servers/year | 1,752,000 |

A provisional 200–400 bytes per observation including indexes gives approximately 7–14 MB/server/year, or 350–701 MB/year for 50 servers. These are planning assumptions, not measured production storage sizes. Backups, replicas, and other overhead are additional. Continuing Decal ingestion makes polling volume additive.

The user measured one server over a seven-day window (server identity not confirmed in the discussion):

- 2,105 observations, approximately 301/day.
- Mean inter-observation gap: 4.78 minutes.
- Median: 0.485 minutes, approximately 29 seconds.
- 90th percentile: 11.63 minutes.
- 95th percentile: 22.54 minutes.
- Longest completed gap: 210.56 minutes.

This demonstrates bursty sampling: regular polling fills long silences but is coarser than some existing Decal observations. Adding 15-minute polling would add 672 observations/week, approximately 32% above that measured week's volume if Decal activity remains unchanged. This one server is not evidence of fleet-wide sampling frequency. Gap percentiles are not time-weighted freshness measurements.

## Implementation design and outcome

Core behavior below is agreed where noted. The implementation uses a separate empty-by-default YAML registration map, Sidekiq dispatch and independent poll jobs, and MongoDB-backed mutable per-feed state. See `docs/population-polling.md` for operational details.

### Endpoint and population definition

- Explicitly registered HTTPS GET URL; suggest `/population.json` without requiring that path.
- `Content-Type: application/json`, UTF-8.
- Agreed response contract: a JSON object requiring only nonnegative integer `count` and integer Unix-second `updated_at`. Allow and ignore additional fields; do not require `schema_version`, `server_id`, or `server`. Bind identity from the approved registration and assign `source: "server"` internally. Extra fields must not override identity/provenance or be mass-assigned into stored observations.
- Agreed: count connected in-world player characters using the same definition as the game/plugin, including bots, multiboxed characters, staff, and test characters. Do not count unique humans/accounts or apply operator-specific exclusions. A genuinely measured empty world may report zero; inability to measure must not be represented as zero.
- `updated_at` denotes measurement time, not the last time the number changed. A new measurement may have the same count. This contract needs to be explicit with operators: merely re-serving an old count must not renew its timestamp.
- A dynamic endpoint or atomically replaced static snapshot can work. An exporter unable to measure the game must not invent zero or renew an old measurement's timestamp.
- No character identities or personal information are needed.

### Timestamp validation and polling state

- Agreed: accept a valid measurement if `last_accepted_updated_at < updated_at <= floor(response_received_at_epoch_seconds)`. No maximum-age gate: old but previously unseen measurements can add valid history. A first measurement has no previous cursor to exceed.
- Agreed: use actual response-receipt time, not request-start time, as the upper bound. This accommodates live measurements generated while the HTTP request is in flight. No additional future/clock-skew grace.
- Capture response-receipt time before delayed parsing/database processing. Do not compare with scheduled job time or previous check plus 15 minutes. Compare integer epoch seconds consistently, without rounding to the nearest second.
- Require timestamps to be JSON integers in seconds; reject missing values, strings, fractional values, millisecond timestamps, and invalid/unreasonable values rather than guessing units or timezone corrections.
- Require a new measurement's timestamp to be greater than the latest durably accepted timestamp for that feed. Same timestamp/same count is a duplicate; same timestamp/different count is a conflict, not a correction. Older timestamps do not create new observations.
- Apply this per-feed cursor only to polling. Do not compare it against Decal timestamps or suppress Decal observations.
- Agreed: keep one mutable polling-state record per registered server with last check time, last outcome, bounded error summary, last accepted provider timestamp, and consecutive failure count. Do not permanently append a record per attempt. Accepted population observations are separate append-only records; failures never enter `player_counts`. Duplicate, regressive, invalid, and failed checks do not renew population age. An accepted old measurement retains its old as-of time.
- Only successful durable ingestion advances the accepted-measurement cursor. Rejected future timestamps must not poison it; database failure must leave the measurement retryable.
- Prevent overlapping poll jobs and enforce idempotency durably by feed identity and measurement timestamp. A restart or lost Redis key must not allow duplicate observations.
- A repeated document creates no new observation regardless of its age. Measurement age may be tracked diagnostically without making it an ingestion gate. HTTP success does not imply recently measured population data.
- Operators may export whenever they choose. Do not synthesize observations for missed intervals or use aggressive retries to compensate for an operator's slower cadence.
- Handle clock synchronization operationally; do not silently adjust timestamps to make invalid data fit. A clock moving backward may temporarily stop ingestion until measurements exceed the accepted cursor again.
- Accepting late measurements can change past UTC daily maxima. Agreed: leave historical cache policies unchanged and accept visibility after existing expiry; do not invalidate historical caches on polling ingestion. Do not require rollups or provenance tracking for daily maxima.
- Measurement time drives latest-observation ordering and UTC historical grouping for polling (agreed). Retain receipt/check time separately for diagnostics (proposed). Existing Decal timestamps remain approximate receipt-time observations because the plugin does not supply measurement time. This is timestamp-based ordering, not source preference.

### Provenance and mixed sources

- Store the agreed source values on each new observation: `"plugin"` for Decal plugin uploads and `"server"` for operator polling. Do not infer source from polling configuration. Feed identity for polling and separate receipt-time metadata remain proposed.
- Agreed compatibility behavior: interpret legacy records without `source` as `"plugin"` based on the known ingestion path, without a bulk rewrite. Plugin measurement time is currently approximate, not an exact timestamp supplied by the plugin.
- Store source internally, but do not add source to UI, public API responses, or other public outputs in this PR. Explicitly prevent serializers that currently return raw document fields from leaking the new field (notably `/player_counts/:server.json`). Do not add provenance to daily-maximum calculations or historical charts. Correcting existing UI source wording or displaying per-observation source is deferred; character-upload labels are outside this PR.
- Keep polling configuration (capability) separate from the source of a displayed count (an actual observation).
- Accept both/all streams for participating servers; polling is not an authoritative replacement or a fallback-only mode. No source-preference mechanism is proposed. Select latest by observation time: operator-reported measurement time for polling, and existing approximate receipt time for Decal. A later HTTP fetch does not make an older polled measurement newer than intervening Decal observations.
- Daily maxima remain dynamically computed from raw observations, not separately recorded. Compute the maximum across both/all sources without tracking which source supplied it; never add counts from two sources together. No winning-source selection, provenance tie handling, or source display is needed for historical charts. Group polled observations by the agreed operator-reported measurement time.

### Registration

- Agreed: operators request registration through an issue/PR; maintainers verify ownership and approve the URL before adding a server-to-URL mapping in TreeStats-owned configuration.
- Cross-check operator authority using community-list history and existing contacts. Suggested request details include community UUID, server name, endpoint URL, contact, and snapshot-refresh expectations; exact configuration identity/keying remains an implementation decision.
- Keep registrations separate from autogenerated `data/servers.rb`. Preserving UUIDs during import remains proposed, not a prerequisite agreed for this PR.
- No registration API, operator accounts, tokens, admin UI, or automatic endpoint discovery/polling from the community list in this PR.
- Verify the registered endpoint belongs to the intended server; validate required fields, timestamps, and failure behavior before enabling persistence. Do not require identity fields in the response.
- Support disabling a feed without deleting its history.
- Registration proves an authorized reporting channel, not independently audited population truth.

### Orchestration and safeguards

- Agreed: one recurring scheduler enqueues independent per-server Sidekiq jobs every 15 minutes; the scheduler performs no HTTP requests. Use the existing Sidekiq setup without migrating unrelated background jobs. Modest staggering/jitter remains a recommendation.
- Do not fetch every endpoint serially in one job. Isolate failures, bound concurrency/request duration, and prevent overlapping jobs for the same feed.
- Agreed: do not catch up missed polling intervals after downtime; resume with a current fetch rather than replaying history. Skip obsolete queued polling slots rather than allowing an old backlog to run.
- Use idempotent persistence. Agreed: no automatic polling-job retries; disable Sidekiq's default retries, record failures, and wait for the next scheduled poll. Duplicate, regressive, future-dated, and invalid responses likewise do not trigger retries. An old but advancing timestamp is not rejected solely for age.
- Recheck enabled configuration when a job runs.
- HTTPS certificate verification, public-address/DNS validation against SSRF, no redirects initially, response-size bounds, and strict request deadlines are necessary.
- Do not convert request failures into zero population or expose new public polling-health indicators. A failed feed and an old displayed population are different: Decal may still supply fresh observations. If all polling stops, existing population readers and Decal ingestion continue normally; existing age-based eligibility rules still apply.
- Maintain the agreed bounded per-server polling-state record for operational diagnosis, not public population-feed badges. Detailed errors go to application logs, with no permanent per-attempt database history. Measurement age is derivable from the last accepted timestamp; latency logging and monitoring that detects a stopped dispatcher/worker remain operational recommendations.
- Decide whether to invalidate/refresh current-count caches or accept their additional five-to-six-minute delay. Fifteen-minute polling alone does not guarantee fifteen-minute-fresh UI data.

### Database work and retention

- Keep the existing raw-observation approach for the initial rollout; no retention deletion is authorized.
- Inspect actual indexes, collection sizes, and explain plans before broad rollout. No PlayerCount indexes are declared in the repository, but production may have manually created ones.
- Growing raw-history sorts/aggregations are a more significant long-term CPU concern than fetching tiny JSON documents at this cadence.
- Repeated identical counts with new measurement timestamps remain useful observations. Reingesting the same measurement or retry is different and should not create duplicates.
- Consider latest-per-server state and daily rollups later, based on measurements; neither is required for the initial rollout. Daily rollups, if introduced, do not need provenance. Do not delete raw observations until all relevant readers support rollups.
- Chart output remains one point per server/day even as raw observation volume grows. More regular sampling can change observed daily maxima without underlying population growth.

6. Registration mechanics: exact configuration location/keying and operational handling of endpoint changes. Maintainer-reviewed configuration, ownership verification, and manual URL approval are agreed; self-service registration and automatic discovery are out of scope.
7. Operational implementation details, including durable per-server polling-state storage and any latest-count cache handling. One mutable state record per registered server, bounded error summary, detailed errors in logs, and no permanent attempt history are agreed. Historical caches remain unchanged, and delayed visibility of late observations is accepted.

## Rollout

1. Maintainers review and register a verified HTTPS feed in `config/population_feeds.yml`.
2. Validate the feed behavior using the manual test steps in `docs/population-polling.md` before enabling it.
3. Enable only when a working endpoint is supplied; Hollowtide remains disabled because the previously suggested URL returned 404.
4. Measure storage/query cost and reporting reliability before onboarding more servers or considering rollups.
